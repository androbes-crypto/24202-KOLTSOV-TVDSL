# HW4. Промежуточное представление и базовые оптимизации

Python 3.10+, без внешних библиотек. Вход — аннотированный AST из HW3 (`../hw3/sema`), который
использует парсер HW2 и лексер HW1. Папки `hw1`–`hw4` должны лежать рядом;
если HW3 в другом месте: `export FUNNY_HW3=/путь/к/hw3`.

## Запуск

```bash
cd hw4
python3 -m ir build examples/opt.fun                 # IR до и после оптимизаций + метрики
python3 -m ir build examples/opt.fun --cfg --graph   # + базовые блоки и граф конфликтов
python3 -m ir build examples/opt.fun --live          # CFG с множествами in/out
python3 -m ir build examples/opt.fun --opt const,dce # только выбранные оптимизации
python3 -m ir build examples/opt.fun -O0             # без оптимизаций
python3 -m ir build examples/opt.fun --json          # всё в JSON (для кодогенерации)
python3 -m ir build examples/opt.fun --dot out/      # CFG и графы в DOT
python3 -m ir run examples/opt.fun 'calc(3, 4)'      # выполнить до и после оптимизаций
python3 -m ir test                                   # тесты
python3 -m unittest discover -s tests -v             # тесты + unittest
```

| Флаг `build` | Что делает |
|---|---|
| `--opt LIST` | какие оптимизации включить: `const,alg,cse,unreach,dce`, `all` (по умолчанию) или `none` |
| `-O0` | то же, что `--opt none` |
| `--cfg` | базовые блоки, предшественники, потомки, обратные рёбра |
| `--live` | то же + живые переменные на входе и выходе каждого блока |
| `--graph` | граф конфликтов временных и раскраска |
| `--registers K` | сколько регистров есть; временные, которым не хватило цвета, помечаются «память» |
| `--json` | IR, CFG, граф и метрики до и после в JSON |
| `--dot DIR` | файлы `<функция>.<before/after>.cfg.dot` и `.graph.dot` |

Картинку из DOT можно получить так: `dot -Tpng examples/dot/calc.after.cfg.dot -o calc.png`.

## Формат IR

Трёхадресный код из лекции 6 (слайд 7). У каждой инструкции не больше двух входных операндов и
одного результата (кроме `update` и вызова). Операнд — имя переменной или константа (`5`, `true`).

| Инструкция | Текст | JSON `op` |
|---|---|---|
| метка | `L1_then:` | `label` |
| копирование | `x := y`, `x := 5` | `copy` |
| бинарная операция | `x := y + z` (`+ - * / % < <= > >= == !=`) | `binop` |
| унарная операция | `x := -y`, `x := !y` | `unop` |
| чтение элемента | `x := load a[i]` | `load` |
| обновление массива | `x := update(a, i, v)` — новый массив | `update` |
| длина | `x := length(a)` | `length` |
| вызов | `q, r := call f(a, b)` или `call f(a)` | `call` |
| условный переход | `if x goto L` | `if` |
| переход | `goto L` | `goto` |
| возврат | `return r1, r2` | `return` |
| проверка | `assert x` | `assert` |

Имена:

* переменные Funny сохраняют имя; если в соседних блоках есть две переменные `x`, вторая
  становится `x#2` (перекрытие имён запрещено в HW3, поэтому других совпадений нет);
* временные — `t1, t2, …` (номер пропускается, если такое имя уже есть у пользователя);
* метки — `L<номер>_<вид>`: `L1_then`, `L1_else`, `L1_end`, `L2_while`, `L2_body`, `L3_and` …

Как переводятся конструкции:

| Funny | TAC |
|---|---|
| `x = e;`, `var x = e;` | вычисление `e` сразу в `x` |
| `var x;` | ничего |
| `a[i] = v;` | уже обессахарено в HW2: `a := update(a, i, v)` |
| `if (c) S1 else S2` | `<c> → L_then / L_else`, `L_then: S1; goto L_end`, `L_else: S2`, `L_end:` |
| `while (c) S` | `L_while: <c> → L_body / L_end`, `L_body: S; goto L_while`, `L_end:` |
| условие `c` | `t := c; if t goto L_true; goto L_false` (как в лекции 7) |
| `a && b`, `a \|\| b` | короткая схема: правая часть вычисляется, только если нужна |
| `assert e;` | `t := e; assert t` |
| `assume e;`, `requires`, `ensures`, `invariant` | не попадают в IR (нужны только верификации) |
| конец функции | `return` всех результатов |

JSON одной функции (`--json`, поле `before.ir` / `after.ir`):

```json
{
  "name": "f",
  "params": [{"name": "x", "type": "int"}, {"name": "a", "type": "int[]"}],
  "results": [{"name": "r", "type": "int"}],
  "vars": {"x": {"type": "int", "temp": false}, "t1": {"type": "bool", "temp": true}, "...": "..."},
  "body": [
    {"op": "binop", "dst": "t1", "sym": ">", "args": [{"var": "x"}, {"int": 0}]},
    {"op": "if", "args": [{"var": "t1"}], "target": "L1_then"},
    {"op": "goto", "target": "L1_else"}
  ]
}
```

Для кодогенерации под JVM здесь есть всё нужное: типы всех переменных и временных (`int` → `iload`,
`int[]` → `aload`), параметры по порядку (номера слотов), метки и переходы.

## CFG

Лидеры: первая инструкция, каждая метка, инструкция после `goto`, `if` или `return`.
Пара `if x goto L1` + `goto L2` считается одним двусторонним переходом (как в лекции), рёбра
подписаны `true` / `false`. Обратное ребро `u -> v` — если `v` доминирует над `u` (заголовок цикла).

Живые переменные считаются итеративно по формулам лекции 6:
`in(v) = use(v) ∪ (out(v) \ def(v))`, `out(v) = ∪ in(s)`, `in(exit) = ∅`.

## Оптимизации

| Имя | Что делает | Пример |
|---|---|---|
| `const` | распространение констант и копий внутри блока, свёртка констант, `if true/false goto` | `t1 := 3; t2 := t1 + 4` → `t2 := 7` |
| `alg` | `x+0, 0+x, x-0, x*1, 1*x, x*0, x/1, x%1, x-x, 0-x, x/-1, x==x, x<x …` | `c := b * 1` → `c := b` |
| `cse` | повтор того же выражения в блоке заменяется копией | `t2 := a + b` → `t2 := t1` |
| `unreach` | удаляет недостижимые блоки, `goto` на следующую метку, неиспользуемые метки | ветка `else` после `if (1 < 2)` |
| `dce` | удаляет `x := e`, если `x` мёртвая после инструкции и `e` не может упасть | `t := i * 2`, который никто не читает |

Проходы повторяются по кругу, пока что-то меняется.

Что **не** делается, чтобы не изменить поведение программы:

* `x / 0` не сворачивается и не удаляется, даже если результат не нужен (деление на ноль);
* `x / x` не заменяется на `1` (при `x = 0` должна быть ошибка);
* мёртвые `load`/`update` (выход за границы) и вызовы функций (могут упасть или зациклиться) не удаляются;
* вызовы не участвуют в CSE.

`+ - *` по спецификации Funny считаются по модулю 2^32 и никогда не падают, поэтому их можно и
сворачивать, и удалять. Деление — как в JVM: с округлением к нулю.

## Граф конфликтов

Вершины — временные. Ребро `t1 — t2`, если `t1` определяется в точке, где `t2` жива (и наоборот).
Раскраска жадная (лекция 6, слайд 39): вершины по убыванию степени, каждой — наименьший цвет,
которого нет у соседей. С `--registers K` вершины с цветом ≥ K помечаются как «память».

## Структура

```
ir/
  tac.py       инструкции и функции IR, текст и JSON
  gen.py       генерация TAC из аннотированного AST (HW3)
  cfg.py       базовые блоки, CFG, доминаторы, обратные рёбра, живые переменные, DOT
  opt.py       оптимизации
  regs.py      граф конфликтов и жадная раскраска
  interp.py    интерпретатор TAC (для проверки оптимизаций)
  testing.py   прогон тестов
  __main__.py  командная строка
tests/
  ir.txt       программы и ожидаемый IR после оптимизаций
  run.txt      программы и вызовы с ожидаемым результатом
  test_hw4.py  unittest
examples/      *.fun, вывод *.out.txt, opt.json, dot/
REPORT.md      отчёт
```

## Тесты

* `tests/ir.txt` — 15 программ: примеры из лекции 6 (слайды 8, 30, 31, 33), пример из P07, задача
  4a из тренировочного варианта КР1, деление, мёртвые `load`/`call`, `&&`/`||`, двумерный массив,
  несколько результатов, одно имя в соседних блоках, константные условия, `assert`/`assume`,
  выражение с большим числом временных. Эталон — IR после всех оптимизаций.
* `tests/run.txt` — 8 программ с вызовами и ожидаемыми результатами: рекурсия, деление как в JVM и
  деление на ноль, переполнение, выход за границы, короткая схема `&&`, копирование массивов, `assert`.
  Каждый вызов выполняется и до, и после оптимизаций.
* **Сравнение до/после:** все программы из `ir.txt`, `run.txt` и `../hw3/tests/positive.txt`
  выполняются на 30 случайных входах. Результат без оптимизаций должен совпасть с результатом после
  каждой оптимизации по отдельности и после всех вместе (включая ошибки выполнения). Случаи с
  неопределённым поведением (чтение неинициализированной переменной) пропускаются.
* `unittest`: CFG примера из лекции (4 блока), обратное ребро цикла, у соседей в графе разные цвета,
  `--opt none` не меняет IR, оптимизации не увеличивают код, отдельные проходы, формат JSON.
